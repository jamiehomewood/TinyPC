# Igloo Room Playbook (generic – copy into every room project)

**Claude: read this before doing anything in a project that runs in the Igloo room.** Then read the project's own errors file (e.g. `errors-log.md`) if there is one.
Generic mistakes (room, tools, file handling) go in the log at the bottom of THIS file. Project-specific mistakes (a character, a scene) go in the project's own errors file.

---

## 1. Working rules (always)
- **The local project folder is the source of truth.** Put new files there. No git commits or pushes unless Jamie asks.
- **Check folder access first.** A PC folder only links to a session started with it attached in the Claude desktop app. Mobile/web chats can't reach it. If there's no access, say so in the first reply and offer files instead.
- **Look at what's already on disk before building.** Another session (or one that ran out of credits) may already have built part of the request. List the folder newest first (`ls -lt`), read files changed since your notes, and build on them. Never write a new file or module before checking one doesn't already do the job.
- **Change only what Jamie named.** If a request could mean two things, ask. (e.g. "rename the feed" means the Spout sender name, not the app.)
- **Test from the student's viewpoint**: centre of the room, about 1.12 m eye height, before building a feature out.
- **Say what is untested** (real Spout feed, the physical room) rather than implying it works.
- **Finish the whole room, not just the inside:** what is seen through every window and door counts. Never leave a placeholder backdrop.
- **UK by default:** scenarios are for UK students. Use UK settings, fittings and photos (check a photo's location data, e.g. Poly Haven coords) and say when no UK option exists.

## 2. The room
- **Rooms** (presets/rooms.json; inside wall faces, measured from Jamie's scans in `RoomBuilder/new rooms/`, which import at 1/100 scale): **Peterborough** (the Igloo room) 6.40 × 5.71 × 2.244 m; **Helmore big room** 5.36 × 6.36 × 2.815 m (doors on two walls); **WHB 406** 5.04 × 7.71 × 2.915 m (one door near a corner). Projection centre = half the room height. Scan north (+y) is assumed to be the builder's north.
- Peterborough size: 6.40 × 5.71 × 2.244 m. Flat walls, projected on the **walls and the floor only. The ceiling is NOT projected** (it's black; confirmed by Jamie with photos, 26 Oct 2026), so anything above 2.244 m on the walls is lost.
- **ICE web layers must be 2:1:** turn Dynamic Resolution off and set the layer to the render's size (e.g. 6144 × 3072). Dynamic Resolution gave 11620 × 3820, which stretched the equirect and pushed the floor about half a metre up the walls. There are 5 more rooms of different sizes (not yet measured).
- **Every 360 render must be built at the size of the physical room it will play in** (walls on the real walls, ceiling at the real height). A render of a smaller or bigger space projects at the wrong scale: furniture lands on the floor and the tops of walls fall off the projected area. Show a smaller place (a cell) at the room's size; walls can be pushed back with alcoves, never brought in.
- Single PC runs Igloo Core Engine (ICE). The room has its own tablet that can act as a remote.
- The room PC is on a **different network** from students' phones.
- On the room PC, a normal browser plays YouTube silently; as an ICE layer it plays with sound.

## 3. Getting something into the room
**In the room:** a three.js page served locally, added in ICE as a **web layer** set to 360 / equirectangular. Audio works in the web layer. No OBS needed.

**On Jamie's dev PC (no ICE):**
- **Spouty** – Electron app replacing OBS + Spout plugin. Loads the page offscreen (default 4096×2048) and sends a Spout feed named **`spoutyfeed`**. Its `config.json` overrides new defaults, so delete it or retype after an update. To change page: type the URL, then **Load** or Enter (the box is orange until loaded; "Showing:" is the page actually sent). `http://` is optional, hand edits to `config.json` apply live, and still pages are re-sent a few times a second.
- **IglooPreview** receives the Spout feed. If it works in IglooPreview, it works in the room.
- **spoutyPreview** – stand-in-the-room viewer for a Spout feed: stand at the centre, turn your head, faint room edges. Settings in an INI file. Its room edges show at once whether a render's walls sit on the real walls.
- **spoutyModel** (`D:\Projects\01_Active\spouty\spoutyModel\spoutyModel`, port 8010) – three.js web app for projecting and handling 3D models (look-around / handle mode, cutaway, show/hide parts, Environment mode for full room scans, Sketchfab zip upload). One Python stdlib server serves the operator view, the ICE web layer and the tablet.
- **Room Builder** (`D:\Projects\01_Active\RoomBuilder`, http://localhost:8030; GitHub `jamiehomewood/SpoutyRoomBuilder`) – builds scenario rooms from a JSON spec (room size, alcoves, doors, windows, arches/kitchens, models, views) and renders Cycles equirect panoramas in Blender with a queue and a library. **Room type** (style: modern = home / hospital / court / custody / outdoor) sets lights, doors, corridors and kitchen layout and fills in default **finishes**; **finishes** (walls, lower walls, floor, ceiling, trim, kitchen; any colour) and **condition** (new / lived_in / worn / neglected / derelict) are separate spec keys, defined in `presets/finishes.json`; `wall_finishes[<wall>]` and an alcove's `finish` override them. Floor tiles: checks (colour2) only on square sizes, `layout` straight/diagonal (diagonal is the default for checks). Old "neglected" style = home + neglected condition (both builder and generator convert it). Wallpaper/carpet patterns are own-work masks in `textures/patterns/` (`tools/make_patterns.py`); the live preview draws the finishes as canvas textures (scene.js finishTexture/worldUVs). Models sit on the furniture under them when dragged (`it.sit`, `it.z`); the model panel has a Height slider. Outside = a Poly Haven HDRI per room (`presets/outside.json`, UK photos where they exist, cached in `textures/hdri/`); doors open onto a style-aware corridor or outside; outdoor scenes are the HDRI plus models on a shadow-catcher ground. `builder/live.html` is the live plain layout for Spouty; `builder/pano.html?lib=<id>&view=<v>&raw=1` shows a finished render full-window. Standard quality (6144×3072, 256 samples) takes about 1.5–4 min per view on the RTX 5070 Ti. Own models (rb_*: ward, court, custody, park) are made by `tools/make_ward_models.py -- <ids>`. **Own models (FBX, OBJ, GLB/glTF, STL or a .zip with textures)** go through `/api/catalogue/upload` → `tools/import_model.py` (Blender: one GLB, real size, footprint centred, standing on its base, front +Z, 256 px thumbnail); they become `up_*` catalogue entries usable in renders and tours. To push a whole wall back, use one alcove the full width of that wall; two full-height alcoves meeting in a corner open the corner up (no pillar). Alcoves carry the room's skirting, coving and lower-wall finish. **Git:** the PC folder is not a git repo. The repo holds code only (no config.json, renders, HDRIs or .glb files; see its .gitignore). A new session clones the repo into the cloud workspace, copies the changed PC files in, commits and pushes (only when Jamie asks or as part of agreed work); the cloud copy does not survive between sessions.

**Scare layer (`builder/halloween.html?lit=<id>&dark=<id>`):** crossfades a lights-on and a lights-off render of the same room (spec `"lights_on": false`, `light_level` dims the pendant), adds flash, glow and shake in a full-screen shader, and draws 3D effects (spiders, pumpkin face, ghost, bats, figure at the window, door leaf, floor hole) in a cube-camera overlay hidden behind an invisible depth-only copy of the room. Sound is procedural WebAudio (HRTF panning, generated reverb) and needs one click or key press before it starts. The timeline is an 8-minute loop (`cycle=` to change); keys trigger each scare. Effects on the floor are only shown briefly, in the dark, as part of a scare.

**Tour Builder (`builder/tours.html`, built 27 Oct 2026):** joins library renders into a tour / branching scenario / escape room. Saved as `RoomBuilder/tours/<id>.json` (API `/api/tours`, removed ones to `tours/_removed`). Markers by yaw/pitch in degrees (yaw 0 = image centre = Front wall, + right; pitch 0 = eye height): `go` (target room; `requires` item ids and/or a `code`), `info` (card), `question` (options with correct / feedback / go / give; `retry`), `item` (an object: `take` true = into the bag, false = look only and put back; often `hidden`, found by tapping within `radius`°; `show3d` stands its catalogue model live in the room on a surface `h` m high), `use` (a person or place that takes items, right/wrong outcomes). Any marker: `hideLabel` hides its label in the room (the tablet still names it). Items: name, catalogue `model`, description, pages; combining items makes new ones. Rooms: `intro`, `cardWall`, `end` + `endText`, `dims` copied from the library meta. Player `builder/tour.html?tour=<id>` (`&look=1` drag-to-look, `&room=` start room, `&sound=0`); 2D overlays are drawn in 0.1° units (3600 × 1800); live objects come from `builder/tour3d.js` (cube camera at the eye → equirect, lit by the room render). Cards sit in the middle of the nearest wall between about +17° and -14°; "Carrying: …" sits on the floor near the corner left of the card wall. Held objects: shown big left of the card wall, turned from the student tablet (`play.html`, pad) or arrow keys; flat things (notes, clipboards) are stood up facing the viewer. The scene server serves the same file as `/rbtour.html` (catalogue under `/rb-static/`), and lists tours on the tablet (group "Tours"). Example tour: `example-discharge-home`.

**Tour player additions (3 Nov 2026, for TinyPC; `TinyPC/tools/engine_patch_2026-11-03.py`, originals in `RoomBuilder/_backup_2026-11-03_tinypc/`).** All opt-in; old tours unchanged (Glenda example checked). Fields are kept when a tour is edited in Tour Builder (it saves the whole object), but the editor has no controls for them yet: edit the JSON.
- **Flags** (hidden progress, never in the bag): `accepts[].flag`, question `options[].flag`; anything that takes `requires` accepts item ids or flags.
- **`accepts[].requires` + `notYet`**: the item is only taken once those are in place (paste before the cooler).
- **Sounds:** `accepts[].sound`, `room.enterSound`: "yes" / "no" / "tick" / "door" or a beep code `post:<S/L/space>` (PC-speaker square wave, 1 kHz: "post:S" all fine, "post:LLL").
- **`lockedGo`** on a go marker: `{ "<item or flag>": "<room>", "*": "<room>" }` → go to the room for the first missing requirement instead of the locked message (fault rooms).
- **`room.ambient: "fan"`**: looping fan hum (filtered noise + 95 Hz hum) that spins up over 2.5 s; stops in a room without it.
- **`room.props`**: catalogue models always standing in the room (yaw/dist/h/turn/size like show3d), optional `spin` (turns per minute about the model's own front-back axis through its middle, `axis` x/y/z). Live objects draw over the render with no depth test, so only put them where nothing in the render is in front (TinyPC's `check_rotors.py` ray-tests this).
- Tested in the built-in browser on the room PC's Room Builder (3 Nov): flags, requires/notYet, lockedGo, props spinning (≈30% of the 3D pixels change per 0.4 s); sounds not yet heard by a person.

**Serving:** Python stdlib server started by `start-server.bat`. It finds a working Python, skips the Store placeholder and works from network drives. Its "next free port if 8000 is taken" fallback doesn't work on Windows: `http.server` sets SO_REUSEADDR, so a second server binds the same port and requests can go to the older one (check `netstat -ano` for two listeners).
**Tablet scene buttons:** add `{id, label, url}` entries to `scenes.json`; nothing else is needed. Room Builder library rooms and Tour Builder tours are listed automatically. Scene controls come from `remote.js`: types toggle, slider, select, button, text (display only), code (typed answer, `{v, n}`), pano (tap on a 360 picture, `{yaw, pitch, n}`; `n` is new on every tap), inventory, turn (absolute angles from the pad). A scene may change its controls list while running: change the array in place and call `Remote.report()`. `control.html` = facilitator tablet; `play.html` = student tablet (controls marked `staff` are hidden there).
**Continuous controls (drag pads, sliders) over the remote:** throttle sends (about every 70–80 ms while dragging), never debounce, and have the scene glide to each new value over about 0.2 s (time-based easing). Add a small dead zone at the start of a drag.

## 4. Design rules for room content
- **Floor projection:** anything at floor level gets smeared across the real floor. Keep floor objects low and against walls (or in alcoves beyond the wall line); check with a floor overlay. Outdoors, keep props about 3.3 m+ from the centre so they land on the walls. **Nothing on the projected floor, even in small rooms:** if furniture needs space, push the whole wall back rather than standing it in the room. (Short status text like "Carrying: …" may go on the floor near a corner: Jamie asked for that.)
- **Alcoves should look like the real place:** a narrow recess round one item (e.g. a toilet) reads as a cubicle with a stray wall beside it. Prefer pushing the whole wall back (full-width alcove) so the room stays a plain box. Alcoves are part of the room: same skirting, coving and wall finish.
- **Options should combine, not come as bundles:** what a surface is made of, its colour and how worn it is are separate choices, so any room type can be any decoration in any condition. The same goes for kitchens. But don't offer combinations that don't exist in real life (e.g. a two-colour check on metro tiles).
- **The preview must show what will render:** patterns, tile layouts and chosen colours, not just a flat average colour.
- **Basic placement belongs in Simple mode:** moving, turning, raising and putting things on tables must not be hidden in Advanced.
- **Moving effects (scare layer, characters) go just in front of the walls**, at real size and above the floor line, so they land on the projected walls. Something placed 1–2 m from the centre is smeared huge across walls and floor. Keep everything where it lands on the walls between about 0.3 and 2.1 m: the ceiling isn't projected (bats placed by their wall-landing height).
- **The cut-off line:** the walls are projected up to the room height only (Peterborough: about 20° above eye level from the centre, a little more towards the corners). Anything above that is lost on the unprojected ceiling, so what a scene is *about* must sit below it; tall things may run off the top on purpose. Draw the line on every draft (TinyPC's `tools/check_render.py` works for any Room Builder panorama).
- **Viewpoint:** everything must read from the room centre. (Downward stairs, for example, weren't visible from there; a raised judge's bench needs enough height and light to read behind the clerk.)
- **Nothing bright straight overhead:** a light at the zenith smears into a band across the top of an equirect. Put ceiling fittings off-centre.
- **Outside:** use a real 360° photo (HDRI) as the world: it looks right from a fixed camera and lights the room. Modelled lawns/fences look fake. Check the view through each window in a close-up test view.
- **Exposure:** bright clinical rooms (pale walls, panel lights) blow out at the modern exposure; check the draft for washed-out whites before the full render.
- **Colours in models:** glTF base colours are linear, so they render much lighter than they look as numbers. Dark woods need values like (0.2, 0.1, 0.045); compare a model against the room materials in a draft. Finish colours in `finishes.json` are sRGB hex and converted to linear by the generator; in three.js canvas code, mix colours in sRGB (`getRGB(..., SRGBColorSpace)`), not THREE.Color's linear values.
- **Tiles on walls:** texture coordinates for brick/tile patterns on vertical surfaces must run along the wall and up (wall=True in brick_tiles), not across the floor plan. Cycles' checker texture has one square per unit at scale 1.
- **Photosensitivity:** flicker effects stay under 3 changes per second.
- **Performance:** modest polygon counts, 2K textures.
- **Realism first:** a "basic" first pass got rejected; aim for the realistic version (e.g. a Cycles 360 panorama with live characters composited in three.js).
- **Text on the walls:** cards in the middle of a wall, between about +17° and -14° from eye height; body text about 2° high (roughly 10 cm on a wall 3 m away). Long text shrinks to fit. Keep cards clear of anything held up beside them.
- **Before delivering a render:** check it is built at the physical room's size, limbs and joints bend the right way, objects touch the floor or surface, scale and orientation are right, there are no light leaks or clipping, windows and doors show something believable, nothing is out of place for the setting (e.g. no radiator in a custody cell), and there are no stray walls, stubs or pillars the real place wouldn't have. Judge floor patterns from a top-down reprojection of the equirect, not the curved panorama.
- **Licences:** Poly Haven (CC0) and Sketchfab CC0/CC-BY only in tools; CC-BY credits go with the images. BlenderKit assets must not be pulled into a tool or shared library. No real coats of arms or logos (e.g. the Royal Arms) in models.

## 5. Tool and file-handling gotchas
- **Sandbox vs PC:** Read/Write/Edit/Bash act on the cloud sandbox, not the PC, even with the same path. Use device_bash for the real disk.
- **device_commit_files** can send a stale copy, even to a new device filename, when the same staged source path is committed again. For every changed file: copy it to a fresh staged path (e.g. `/mnt/user-data/outputs/stage_x/<name>`), commit to a new device name, `mv -f` over the target, and check `md5sum` both sides. (Happened again when a staging folder was reused for a second version of app.js.)
- **Writing files straight onto the PC:** device_bash heredocs work, but one command must stay under about 30 KB (Windows command-line limit, error "spawn E2BIG"): write big files in parts (`cat >` then `cat >>`), then `node --check` / `py_compile` on the PC. For edits, patch with a short Python read-replace-write that asserts each old string occurs once.
- **Running Windows programs:** the PC shell (device_bash) is a Linux VM and can't reach Windows localhost. To run Blender or a Windows Python server, start it with `subprocess.Popen` from the Blender MCP (`execute_blender_code`, `sys.executable` = Blender's Python; `result` must be a dict) and test it with urllib from there. The Blender CLI MCP tool can't find blender.exe (it is `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe`; Popen it with `-b <file.blend> -P <script>` to inspect a saved room, writing results to a file and catching exceptions). Never run `read_factory_settings` in Jamie's open Blender session: launch a separate `blender -b` process. Keep Blender MCP calls short (no long polling loops): they freeze Jamie's Blender while they run. Poll files with device_bash (timeout max 180 s). For slow API calls (imports), Popen a small Python script that writes its result to a file. Restart the test server after changing server.py.
- **Test servers on Windows:** check `netstat -ano` first and look up what's listening (PowerShell `Get-CimInstance Win32_Process` for the command line); pick a free port (two servers can share one, see Serving). Port 8000 is usually Jamie's own scene server: leave it alone. To test Room Builder's web side next to Jamie's running copy, run `server.Handler` from a small script without the render worker (`_to_delete/tourtest_rb.py`), never a second full server.py (its worker would take queued renders). Stop test servers by PID (`taskkill /PID <pid> /F`) when done.
- **Built-in browser (desktop app) for real UI tests:** it can open the Windows localhost servers started from Blender. Each new localhost port asks for access (request_access; "site" sticks after a few). Background tabs pause requestAnimationFrame and throttle timers to about 1 s, so front the page under test (including the tablet page when timing its sends). Emulated viewports wider than the pane give odd screenshots; use 720 × 360 for a 360 page.
- **Deleting on the PC:** not allowed by default; move test files to `RoomBuilder/_to_delete/` for Jamie to clear.
- **Blender scripting:** after setting `location`, call `bpy.context.view_layer.update()` before reading or multiplying `matrix_world` (it is stale until then). Blender's Python has no Pillow: make images (pattern masks) in the cloud workspace and copy them over.
- **Blender world HDRI orientation:** with Generated coords and no rotation, the image centre faces -X (west); Mapping rotation z = +θ turns it anticlockwise from above. three.js sphere (scale -1 on x): rotation.y = -θ matches.
- **Git on the PC:** the shell has no GitHub access and no git-lfs. For status checks use `git -c filter.lfs.process= -c filter.lfs.smudge=cat`; do LFS work in the cloud workspace.
- **New GitHub repos:** this session can't create repos or change repo settings (visibility etc.); only repo-scoped git/API work. Jamie makes the repo, then add_repo with push access. Check visibility after the first push (`gh api repos/<owner>/<repo> -q .private`) and tell Jamie if it isn't what he asked for.
- **Git lock files:** request delete permission on the folder before fetch/checkout/reset on the PC.
- **LFS assets:** a shallow clone leaves pointers. Use `git lfs pull --include="<path>"`, or `media.githubusercontent.com` URLs.
- **Scenes in an iframe:** send IPC/keys to every frame (`mainFrame.framesInSubtree`), not just the main frame.
- **Windows exe builds:** Jamie's PC runs Python 3.14, which lacks some wheels. Build in a private Python 3.13 venv with `--only-binary=:all:` (pygame-ce for pygame). Don't touch his main Python. Bundle VC++ runtime DLLs with Electron apps.
- **ElevenLabs SFX:** set `duration_seconds` and `loop: true` via `creative_update_node` before generating, or you get about 2 seconds.
- **Headless testing:** Playwright Chromium with `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`. Test UI controls by actually using them (open a dropdown and pick an option, check rows at the real panel width), not just by loading the page.
- **Colour pickers:** `<input type=color>` fires `change` only when the picker closes; handle `input` too so the colour applies live.
- **UI cards with click-to-select:** a click handler on a card or its header must ignore clicks on controls inside it (select, button, input, label), or the redraw kills the control.
- **Hiding elements:** never rely on the `hidden` attribute for an element that has a CSS `display`; set `style.display`.
- **Wall names for Jamie: Front, Right, Back, Left** (from the room centre facing the middle of the 360 image), not north/east/south/west. The builder shows these; spec files keep the compass names (front = north, right = east, back = south, left = west).
- **Orientation conventions (Room Builder):** spec x = east, y = north; three.js (x, z, -y). A model whose front faces -Y faces into the room from the north wall at rot 0, south 180, east -90, west +90. Equirect centre = north; east is to the right. Beds: head at +Y, so rot +90 puts the head against a west wall.
